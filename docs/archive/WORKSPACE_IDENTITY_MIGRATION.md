# Workspace identity foundation: deployment notes

This is a foundation only. Workspace creation, invitation binding and a workspace selector are not implemented. Do not deploy the migration without the application update and a reviewed identity reconciliation plan.

`identity_memberships` binds a validated token issuer and subject to an existing tenant user. A binding has independent active and owner flags; the tenant user's active flag and existing role assignment still apply. Existing user IDs, roles, records and audit actors are not rewritten. A user without a binding retains legacy access only when their user ID exactly equals the verified subject from the configured canonical issuer or its accepted `/auth/v1` alias. Email is never used to resolve a membership. Existing accounts previously matched only by email therefore need a reviewed binding before deployment; the database alone cannot prove which provider subject owns an email. Do not automatically merge those accounts or infer ownership from their role. Existing users without a binding have no asserted owner flag.

Before deployment, inventory existing users, their roles and provider identities through approved administrative sources; resolve mismatches and multiple roles manually. Bind the exact trusted issuer and subject to the existing `(org_id, user_id)` only after verification. No self-service binding endpoint is provided. The migration removes global email uniqueness while retaining per-workspace uniqueness. Review any other operational tooling that assumes globally unique emails. Downgrade is deliberately blocked because restoring global uniqueness could lose valid multi-workspace identities.

The application role has no direct access to the binding table. PostgreSQL membership lookup uses a narrowly scoped SECURITY DEFINER function. Since existing tenant tables use FORCE RLS, the migration checks that its function owner has BYPASSRLS or superuser privileges; review that privileged role and ownership before running it. The old email-based lookup is revoked. Coordinate schema and application rollout: older application versions cannot use the revoked lookup, and new code cannot resolve membership before migration 010 is installed.

With multiple active memberships, `/api/v1/auth/me` returns `WORKSPACE_SELECTION_REQUIRED` and the available workspace IDs without selecting a workspace. Supply `X-Tenant-ID` to select one; the server validates active membership and role on each request. No workspace-switcher UI is included in this phase. Membership lookup errors return 503, not an empty membership result. Revoking either the binding or tenant user prevents access; ownership alone does not grant a role.

The existing frontend does not yet handle `WORKSPACE_SELECTION_REQUIRED` and must not be presented as a finished multi-workspace experience. The existing invitation acceptance path has not been adapted to create these bindings for an identity already in another workspace, or to independently establish verified-email proof. Do not rely on it for multi-workspace onboarding until that work is complete.

## Platform operator prerequisite

`PLATFORM_OPERATOR_SUBJECTS` is a comma-separated list of authenticated identity subjects allowed to use platform-wide backup and human maintenance endpoints, in addition to their existing role checks. It defaults to empty, which denies all human operators. Configure and verify the existing authorized operator subjects before deploying that safeguard; it intentionally changes access to those endpoints. Scheduled service-account authentication remains separate. This safeguard is advisable before self-service workspace owners receive `SYSTEM_ADMIN`, because that role previously also reached platform-wide operations. It can be released separately from the identity migration, but must not be omitted when self-service administration is enabled. Confirm issuer configuration and subject provenance, operator recovery and access review before rollout.

The PostgreSQL tests require a disposable migrated database named with an `_test` suffix and `TEST_POSTGRES_URL`; they create test records and are not for an application database. Verify migration upgrades, existing access and audit attribution, unauthorized selection, revocation, restricted-role lookup and pooled tenant-context reset before any release.
