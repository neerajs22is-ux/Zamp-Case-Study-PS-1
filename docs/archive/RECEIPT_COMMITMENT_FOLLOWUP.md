# Receipt commitment hardening follow-up

The existing gate compared each invoice against accepted receipt quantities but did not subtract quantities on earlier approved or second-approval-pending invoices. Two six-unit invoices could each pass against a ten-unit receipt when the PO amount ceiling was large enough. Matching now includes committed lines, rejects unidentifiable prior lines or missing prior quantities, conservatively blocks a prior partial monetary approval without a quantity allocation, and checks cumulative authorized and received quantities. Approval rechecks this under the existing shared PO row lock. No historical records or financial rules were rewritten.

Evidence: `tests/test_receipt_commitments.py` creates a synthetic ten-unit receipt and two six-unit invoices; it requires gates 3 and 6 to fail for the second invoice. `tests/postgres/test_migrations_and_financial_concurrency.py::test_concurrent_approvals_cannot_reuse_receipt_quantity` exercises simultaneous approvals with a sufficiently large PO amount, so the receipt quantity is the limiting factor. The final broad offline results are in `inspection-evidence/receipt-final.txt`; 57 focused existing checks and the new SQLite regression also passed. The disposable PostgreSQL selection passed **47** tests (`inspection-evidence/receipt-postgres-final.txt`).

This is a conservative local commitment calculation, not a general receipt-allocation ledger. It uses the currently selected receipt snapshot and exact PO line identity. Multiple receipt aggregation, partial-quantity allocation, supplier credit notes, upstream ERP synchronization/freshness and external commitments remain unsupported. Existing historical approvals are not changed. No migration or new runtime configuration is introduced.

Guidance: [PostgreSQL 17 row locks](https://www.postgresql.org/docs/17/explicit-locking.html) and [OWASP API Security Top 10 2023](https://owasp.org/www-project-api-security/) were consulted as relevant primary references. The former explains serialization by row locks; the latter provides categories for future authorization and resource-consumption review. Neither is a penetration test. Existing Python 3.12.10, PostgreSQL 17.11, SQLAlchemy 2.0.45, pytest 9.0.3 and the repository's disposable runners were used; no new external repository or tool was adopted. Karpathy guidelines were applied for a narrow change.

The wider requested review of authentication/session revocation, model spending/rate limits, secret/dependency hygiene, recovery, onboarding, tax/currency, source freshness and corrections remains incomplete in this follow-up. No live-provider retest, browser testing, load test or penetration test was performed. The earlier live-provider results remain historical evidence, not proof of the modified code. Deployment and production readiness are not claimed.
