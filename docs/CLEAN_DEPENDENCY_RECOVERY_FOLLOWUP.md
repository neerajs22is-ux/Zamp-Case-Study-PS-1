## Clean dependency graph

The repository has no Python production lockfile. `requirements.txt` is the declared input, includes test dependencies, and uses a mixture of pins and minimum versions; this is a clean resolution for Windows/Python 3.12, not a reproducible cross-platform production image. Created `scratch/clean-production-final-3a7f2d8c` without system site packages, installed declared requirements with binary wheels, ran `pip check`, captured `pip freeze --all` in `inspection-evidence/clean-production-final-resolved.txt`, and ran the separately installed PyPA pip-audit 2.10.1 against that environment's `site-packages`. No auto-fix command was used. The resolved pip is 26.3 and boto3 is 1.43.125.

The initial clean scan had 15 entries across three packages, including duplicated advisory records. Six unique pip issues affected the bootstrap pip 25.0.1; upgrading pip and adding `pip>=26.2` to declared requirements removed those entries. A build should update its bootstrap pip to at least 26.2 **before** resolving/installing application dependencies; listing pip in requirements does not protect the earlier bootstrap step. The final scan emitted three entries representing **two unique unpatched advisories** after deduplicating IDs and aliases:

* **Critical component advisory** `PYSEC-2026-4298` / `GHSA-3qf3-8w2g-rqmx` / `CVE-2026-85394`, python-jose 3.5.0, no patched release observed. The demonstrated prerequisite is accepting asymmetric public-key bytes as an HMAC secret when algorithms/keys are not separated. Application auth branches select the configured symmetric secret separately from JWKS asymmetric keys and pass one algorithm; existing DER/HMAC and invalid-signature tests passed. That is a scoped reachability assessment, not proof the dependency has no exploitable paths. Evaluate a maintained replacement with ES256, RS256, HS256 and Google OIDC compatibility before release.
* **High component advisory** `PYSEC-2026-1325` / `GHSA-wj6h-64fc-37mp` / `CVE-2024-23342`, ecdsa 0.19.2, no patch. The advisory concerns side-channel exposure when signing, key generation or ECDH; verification is not affected. The installed python-jose selected `jose.backends.cryptography_backend` for EC and RSA in this clean environment, and the relevant production Google paths verify signatures. The vulnerable package remains installed transitively; backend selection is not an unconditional security guarantee.

Raw reports and alias-deduplicated findings are in `inspection-evidence/clean-requirements-audit.json`, `clean-production-final-audit.json`, and `clean-production-deduplicated.json`. The clean build found two undeclared runtime dependencies: `requests` for Google JWKS and `boto3` for the supported S3 adapter. The Google paths now use the already-declared `httpx` and reject non-success JWKS responses; boto3 is declared. New tests exercise both Google OIDC paths with real locally signed test JWTs and intercepted JWKS responses. S3 provider behavior itself remains untested in a live account.

## Session behavior and recovery

Per-token application revocation remains durable and fail-closed, as described in `DURABLE_CONTROLS_FOLLOWUP.md`. `backend/scripts/prune_revoked_tokens.py` is a separate explicit-target PostgreSQL operator command. It requires `REVOCATION_MAINTENANCE_DATABASE_URL` and `--confirm-expired-prune`, removes only rows expired more than 24 hours according to the PostgreSQL clock, and reports only the count. A restricted application role is denied; a disposable PostgreSQL test verifies active and recently expired entries survive. No scheduler, monitoring or production cleanup was configured.

An optional `AUTH_REJECT_TOKENS_ISSUED_BEFORE` UTC Unix-seconds cutoff rejects signed tokens with missing, invalid or older `iat`. It provides an operator-controlled containment step after restoring a database that might have lost later revocations. It is disabled by default, must be deployed consistently to every instance after the incident time, and can interrupt legitimate older sessions. It does not invalidate provider refresh tokens: those can obtain a newer JWT and require provider-side session revocation or key/identity recovery. Tests cover before, at and absent `iat`.

Supabase documents local and global sign-out as refresh-session operations; already issued JWTs can continue until expiry. The upstream `auth/internal/api/logout.go` inspected on 2026-11-07 falls back to all-user logout when its session lookup is absent, even when local scope is requested. The application does not currently possess an independently verified active provider session or a designated disposable provider project for safe end-to-end validation. No provider sign-out was added or claimed. Global provider sign-out also does not by itself revoke every already issued application access token. Until a verified integration exists, operators must explicitly revoke provider sessions and handle outstanding JWTs with an incident cutoff and appropriate identity-provider key procedures.

## Backup and restore

The existing PostgreSQL exercise creates two synthetic tenants, a document, financial data and an audit actor, backs up from a repeatable-read privileged snapshot, restores into another migrated disposable DB and in-memory object adapter, verifies SHA-256, composite tenant relationships, actor attribution and non-bypass cross-tenant denial, and tests rollback when verification fails. It now asserts the important limitation that a previously written object remains after the database rolls back. No cloud object provider was exercised.

Newly fixed partial failures: failure to enumerate source objects now fails backup instead of silently assuming an empty bucket; failure to retrieve an unindexed object marks the archive failed. Restore refuses an unavailable or nonempty destination bucket before writing any objects. The empty-bucket preflight is not an atomic conditional write: isolate the destination from all other writers for the whole restore. If restore fails after writing any objects, discard or separately clean the owned destination before retrying. Database and object-store operations do not share a transaction. A separate authorized backup operator must have full read visibility and repeatable-read isolation; the application role is not given those privileges. Restore requires explicit DB target and destination confirmation, a migrated empty database, a separate empty bucket, key access, and reviewed provider identity recovery. Production schedules, retention, off-site copies, identity recovery, provider permissions and real object-store failure behavior remain unverified.
